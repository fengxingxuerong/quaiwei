# 地区用词校正（`--variant zh-TW`，v0.9.81）

> 类型：当前口径。改了 `src/engine/regional-zh.ts` 就同步改这份。
> 一句话：给台湾读者看的简体稿，把「软件」换成「软体」、把半角标点收拾成全角。
> **不做简繁转换**——这条边界是刻意的，下面第 3 节解释为什么。

## 1. 为什么单开一个 pass

`humanize()` 的产出挂在本仓的标定棘轮上：18 个送检点、`x` 轴一动就有 6 个漂、`Δ` 天花板
压在 35/35。地区用词跟"去 AI 味"是两件事，混进同一条管线，改一个动另一个，谁都测不稳。

所以它是**后处理**：`humanize()` 照旧，调用方显式给 `--variant zh-TW` 才跑。
不传 = 一段代码都不执行，产出与 v0.9.80 逐字相同（`src/engine/regional-zh.test.ts`
第一条用例就是守这个）。

## 2. 怎么用

```bash
# 单文件 / 目录
ai-humanizer ./稿子 --out ./out --variant zh-TW

# 管道（正文走 stdout，诊断走 stderr）
cat 稿.txt | ai-humanizer --variant zh-TW

# MCP 里也一样，字段名是 variant
{ "name": "humanize_text", "arguments": { "text": "...", "variant": "zh-TW" } }
```

跑完控制台会明说换了什么：

```
ⓘ 地区校正：用词换了 6 处（软件→软体、默认→预设、设置→设定、账号→帐号 等） · 标点 5 处
```

`--report rep.json` 里逐篇落账，形如：

```json
"regional": { "variant": "zh-TW", "terms": [{ "from": "软件", "to": "软体", "count": 1 }], "punctuation": 5 }
```

## 3. 三条边界（别在外面替它夸口）

1. **不做简繁转换。** 字形是 OpenCC 的活。手写一张字表出来，遇到表外字就是混合字形
   （「軟體」旁边还站着「设」），那种稿子比不改更糟。所以这里只换词与标点：
   **输入简体、输出简体**，繁体市场请自己再走一遍 OpenCC。
2. **只换无歧义的词。** `程序`（也可能是 procedure）、`质量`（也可能是 mass）、
   `文件`（也可能是公文）这类一词两义的一律不进表。宁可少换，不要换错——换错是用户
   要自己读出来才发现的那种错。
3. **代码块、行内代码、URL、邮箱一律不动。** 复用 `text-shield` 的区间表，跟去味引擎同一套判据。

标点规则也刻意保守：只在**两侧都是中文**时把 `, ; : ? !` 换成全角，`3,000`、`v1.2`、
`Hello, world` 都不动；半角标点后面跟一个空格时把空格一起吞掉，不产出「， 」这种半吊子。

## 4. 词表

当前 39 条，分信息技术与生活出行两组，见 `src/engine/regional-zh.ts` 的 `TERMS`。
加词的门槛：**这个词在台湾只有一种写法**，且不跟别的含义撞车。测试里有一条
`regionalTerms()` 的倒序断言——词表必须按长度降序，否则「视频会议」会被「视频」先吃掉，
拼出「影片会议」。

扩词时先写用例、再进表：`src/engine/regional-zh.test.ts` 里每条断言都是精确输出比对，
表改了但行为没按预期变，测试立刻红。

## 6. 已知没做的

- **没有 zh-HK / zh-MO**：`ZhVariant` 现在是 `"zh-TW"` 单值联合类型，加的时候在联合类型与
  `applyRegionalVariant` 里各扩一处，词表也要分地区（目前没有分地区的能力）。
- **没有简体化（zh-CN）方向**：台湾稿转大陆说法是反向需求，有人提再评估。
- **不做字形检测**：输入是繁体时这个 pass 基本空转（词表键是简体），不报错、也不猜——
  静默空转比瞎换安全，但用的人得知道。
- **网页版只有开关，没有地区选择**：专业视图里一个 chip（`台湾用词`），开/关两种状态；
  桌面版与网页版共用同一份 UI，所以两边都有。批量面板还没接这个开关（CLI 的批量已经支持）。
