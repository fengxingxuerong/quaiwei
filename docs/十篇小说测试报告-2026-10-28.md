# 十篇小说规模测试（2026-10-28）

> 类型：实测报告。数据都是这台机器上真跑出来的；跑不出来算我写错。
> 目的：给「去 AI 味」做一次 1 万字级叙事长文的规模测试——现有回归语料（`scripts/realcase/`）最长的一篇
> 不到 4000 字，长文的分块接缝、句数累积、代理分漂移这些事，小样本测不出来。
>
> 版本：v0.9.81 工作区（`package.json` 0.9.81，`git log` 最后一提交仍是 0.9.80）

## 1. 语料怎么来的

用本项目自己的 LLM 通道（`deepseek-v4-flash` @ `https://token.sensenova.cn/v1`）生成 10 篇中文短篇小说，
体裁各不相同（都市悬疑 / 硬科幻 / 武侠 / 现实主义家庭 / 校园 / 历史演义 / 玄幻 / 赛博朋克 / 灾难 / 爱情）。

- 生成器：`artifacts/novel-test-1028/gen-novels.mjs`（每篇 4 段续写、段间用上一段末尾 500 字衔接）
- 每篇提示词里给死 5 条「保真锚点」（日期 / 门牌 / 金额 / 车牌 / 编号），用来测数字与专名留存
- 成品：`artifacts/novel-test-1028/novels/`，合计 **101,703 字**（去空白）
- 生成开销：**2808 秒**（47 分钟，4 路并发）
- 生成期的坑（记在生成器账上，不算引擎）：网关会偶发「HTTP 200 + 空 content」，
  第一版生成器把它当成「段落太短」并整篇重跑，浪费约 10 分钟；改成段内自愈后正常。
  n09（灾难）只照做了 5 条锚点里的 1 条（写成「六个小时」而不是「6小时」）。

> 为什么要「AI 生成的小说」当输入：LLM 写的叙事稿正是这类工具的主要输入，
> 且它自带 LLM 的行文习惯（破折号解释、每段一个收束句），比人写的更适合当「待去味」样本。

## 3. 结果

### 3.1 总量（10 篇 / 101,703 字）

| 路线 | 篇数 | 字数比 | 代理分 detectAI ↓ | 引擎自带 aiScore ↓ | 套话命中/篇 | 句长 CV | 每千字句数 | ≤8 字短句 | 原句原样保留 | 丢数字 | 改单位 | 结构缺陷 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `orig` | 10 | — | 13.0 | 21.7 | 0.8 | 0.60 | 40.7 | 10% | 100% | 0 | 0 | 0 |
| `local06` | 10 | 100% | 12.8 | 20.0 | 0 | 0.50 | 52.7 | 10% | **50%** | 0 | 0 | 0 |
| `local09` | 10 | 100% | 12.8 | 20.8 | 0 | 0.51 | 53.1 | 10% | **50%** | 0 | 0 | 0 |
| `deep` | **6**（n07–n10 未跑完） | 90% | 12.0 | 27.3 | 0.7 | 0.60 | 50.9 | 10% | 40% | 1 | 0 | 0 |

读法（三句话）：

1. **本地引擎在这批文本上几乎不改词**：套话命中 0.8 → 0，代理分 13.0 → 12.8。
   它改的是句子——每千字句数 +29%、一半的句子被重切。
2. **两把尺子方向相反**：`detectAI` 说略好（13.0 → 12.0，深度仅 6 篇口径），`aiScore` 说更差
   （原文 21.7 → 深度 27.3）。它们测的不是同一件事（词表命中 vs 结构/节奏），
   同一份稿可以在两把尺子上一个变好一个变差——这正是 README 里「别拿界面降幅判断安全」的由来。
3. **保真这条线是干净的**：本地两档 10 篇 × 5 条锚点全部留存，丢数字 0、单位改动 0、格式缺陷 0。

### 3.2 深度模式（LLM 闭环）的实际情况

这一节必须先说环境：**本机跑批时网关在限流**。隔离实测（单独一段 1100 字）：

```
LLM 轮次分 [8] · 质检 1/1 轮通过（最后一轮候选被弃用：质检通道异常，本轮放行（未实际质检）：
API 返回 429（网关限流，已轮换 Key 并退避重试仍失败…）：{"message":"rpm exhausted","type":"quota_exceeded_error","code":"8"}）
```

也就是说：**1 万字深跑里大量「LLM 未产出」不是引擎写坏了，是把 Key 轮换 + 指数退避全部用光后被网关挡了回来。**

## 5. 发现

### 5.1 本地引擎对叙事长文基本是「只改句、不改词」

10 篇里词表套话命中从 0.8 降到 0，代理分只动了 0.2 分；同时**一半的句子被重切**，
每千字句数 40.7 → 52.7。用户看到的是一份读起来更碎的稿子，分数几乎没降。

这不是 bug（设计就是"换词不换骨"），但它意味着：**对 LLM 写的小说，离线引擎的收益接近零，
代价却是 50% 的句子被改写**。README 那句「纯人写稿越去味官方分反而略升」在这批 AI 叙事稿上同样成立。

### 5.2 破折号被系统性改写，产生大量无主碎片句

原始 10 篇共 148 处「——」，本地档产出只剩 10 处（-93%）。样本（n01）：

```
原文：一股陈旧的霉味扑面而来，混着某种说不清的潮湿气息——像是阴雨天积攒了很多年的湿气，渗进了木头、布面、水泥缝里。
产出：一股陈旧的霉味扑面而来。混着某种说不清的潮湿气息。像是阴雨天积攒了很多年的湿气。渗进了木头、布面、水泥缝里。
```

后三个「句号句」在中文里都不是完整句子。10 篇里这类碎片并不罕见，也是 `每千字句数 +29%` 的来源。

### 5.3 项目自己的「语法塌缩」判据在这里大面积误报

`collapseIssues` 在 10 篇本地档上报了 **126 条**「谓语已丢失」，逐条看多为破折号改写引起的误报：

```
「混着某种说不清的潮湿气息」是原文「混着某种说不清的潮湿气息——像是阴雨天积攒了很多」被截断后的残留，谓语已丢失
```

这句的谓语（混着）明明还在。判据假定「产出是原文小句的严格前缀」＝「尾巴被砍掉＝谓语丢了」，
而引擎是**在破折号处断句**，前半截天然是前缀。5.2 是真缺陷，5.3 是这个真缺陷被误读；
两条要分开修：一条改切句规则，一条改判据。

### 5.4 两处语域错位的坏替身

- `击穿 → 彻底拿下`（`src/engine/humanize-vocab.ts:360`）在 n02 命中，产出「被微陨石**彻底拿下**的太阳能帆板」
- 同类还有 `融合 → 合在一起`（同表 237 行），续写会话里实测「深度融合大模型能力 → 深度合在一起大模型能力」

这类替换不是"更像人"，是把工程设计/军事语域的动词换成了体育营销语域。10 篇里命中率低（各 1 次），
但都是读者一眼能看出的病句——词表里该按语域再加一列，或者把这类替身限制在标题/口语段落。

### 5.5 深度模式在限流下的真实形态是「混拼」

6 篇 71 块里 **35 块回退本地引擎（49%）**；最惨的 n01 是 11 块里 9 块回退、n03 是 8/11。
结果是同一篇稿子前一段是 LLM 自然口语、后一段是本地引擎的碎句——**风格断崖**
（项目自己在 `llm.ts:195` 的注释里写过这个风险，所以回退块强制走 0.5 以下的温和档，
但这一轮里断崖仍然肉眼可见）。

同目录下的两份稿子可以直接对比（n02 开头）：

```
原文：警报声在第七次响起时，周恒正悬浮在第3舱的舷窗前，看着那片被微陨石击穿的太阳能帆板。
深度：警报第七次响起来的时候，周恒在舷窗边上。那片被微陨石击穿的太阳能帆板挂在主桁架左侧…
本地：警报声在第七次响起时，周恒正悬浮在第3舱的舷窗前，看着那片被微陨石彻底拿下的太阳能帆板。帆板像一只折断的翅膀。歪斜地挂在…
```

**诚实结论：这轮 deep 数据不能当"深度模式能力"的证据**，它测的是"网关限流 + 回退链"的行为。
回退链本身及格：有产物、不中断、逐块说明、`engine: mixed` 不冒充 `llm`。

### 5.6 数字保真：本地路径是干净的，深度路径掉两处且都自己说出来了

- 本地两档：10 篇 × 5 锚点 **50/50 全中**，`missingNumericFacts` 0 条、`changedUnits` 0 条
- 深度：n01 掉「407」一次（11→10）、n02 掉「3」一次（17→16），`note` 里都写了
  「忠实度：数字 X 出现次数减少」
- 更深的一处内容丢失也抓到了：n02 原文「氧气余量 62%，这意味着一小时二十二分钟后他们将失去一半以上的储备」，
  深度稿把整句删了，`quantityFacts` 报「22分钟」缺失（原文是中文数字「二十二分钟」）。
  这条同时证明中文数字互认（v0.9.79）在真实长文上是有效的——它认出了「二十二」而不是只认阿拉伯数字

### 5.7 MCP 通道在 1 万字上没问题，但两个分数容易混

`humanize_text` 吃下 10,503 字，83 ms 返回 10,464 字，数字全在，`structuredContent` 完整，协议 2025-06-18。
但同一个响应里 `scoreBefore: 42` 是**引擎自带 aiScore**，而 CLI 汇总里的「代理分 13」是
**detectAI.probability**——两个指标的刻度不同，文档里没并列解释过，容易让用户拿 42 去和 13 比。

### 5.8 审题模式与学术出口在小说上的行为符合边界

- `--detect-only`：0.58 秒读完 1 万字，320 句里标出 3 句，给分 12（判"人工特征"）。
  对 AI 生成的小说几乎没有判别力——这与 README 顶部「低分 ≠ 像人写」是同一件事。
- `--academic-check`：判 **READY**，并在提醒里写明「这轮没找到引用键，引用完整性这一项属于空查」。
  小说不是学术稿，这个结果说明它没有把"不是论文"误判成"不合格"。

## 6. 这次测不了什么

1. **没有外部检测器真值**。三把尺子里只有本地代理分和 LLM 评委，作品一律没过朱雀之类的外部检测。
   按 `SCORECARD.md` 的口径：能说的只有"文本更成句、数字没丢"，不能说"更像人写"。
2. **LLM 评委分（0=人写）本轮普遍 2~10，但它不能当证据**：评委 glm-5.2 与改写模型同在一个网关、
   同一批 Key 池下跑，仍属闭环自评；`docs/judge-anchor-calibration.md` 记过同一文本 55↔84 的方差。
3. **限流让深度数据失真，且只跑完 6/10 篇**。3 路并发的总吞吐被网关配额压死：
   隔离单块实测 102 s 正常跑完，但整批跑起来后同一时刻直连 API 也不断返回
   `429 rpm exhausted / quota_exceeded_error code 8`。改为 2 路重跑剩余的 4 篇，
   14 分钟只推进到第 2 块（约 7 分钟/块，估算还需 2.5 小时），于是主动停在这里——
   **没有把「跑不完」写成「跑过了」**。n10 连深跑都没进：它生成完成时这批已经开跑。
   按实测速率外推：这个账号配额下 10 篇 × 1 万字深跑约需 4~5 小时。
4. **叙事体裁 ≠ 论说文**。本轮所有结论不能外推到政务报告/论文——那类书面文本的
   aiScore 低报问题在 `docs/external-judge-findings.md` 里已经量过（本地 2 / 外部 90）。
5. **没测桌面端**（Electron 壳）、没测历史/批量面板的 UI 行为；这两条走 `npm run smoke:desktop`。
6. **`collapseIssues` 的 126 条不全是真缺陷**（见 5.3）。它不是这轮的主结论，
   但任何用它当质量指标的下游脚本（包括后续可能加进 CI 的）都会在这类「破折号改写」稿上系统性误报。
